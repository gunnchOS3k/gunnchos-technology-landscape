# Publication Master Requirements

# 1. Product identity

## 1.1 Working title

**The Technology Landscape**

## 1.2 Subtitle

**How Computers, Networks, AI, and Devices Create the Experiences We Depend On**

## 1.3 Series identity

**A gunnchOS3k + WAIKE learning system**

## 1.4 Publication category

The work is simultaneously:

- an illustrated technology field guide,
- a textbook,
- a lab manual,
- a systems-thinking guide,
- a technology career map,
- and a bridge into deeper engineering and research.

It must not collapse into only one of these forms.

# 2. Book promise

A person with no technical background should be able to begin with a familiar experience and trace that experience through the physical and digital layers that make it possible.

Representative starting experiences include:

- joining a video call,
- tapping a user-interface control,
- playing a game,
- writing and compiling code,
- using an AI assistant,
- receiving a wearable alert,
- opening a file,
- streaming media,
- connecting from a weak-signal area,
- moving between access networks,
- sending data to a cloud service,
- interacting with a sensor.

The book is not only about computer architecture.

It must connect:

# 3. Governing teaching model

Every substantial topic must ultimately fit the model:

> **Human experience → system → component → code → network → society**

This does not mean every paragraph must discuss all six levels.

It means no technical layer should be presented as isolated trivia.

The reader should understand:

- what the person experiences,
- which system creates that experience,
- which components participate,
- what software coordinates them,
- what data or control crosses a network,
- and what consequences appear when the technology is deployed at human scale.

---

# 4. Non-negotiable reader outcomes

A reader completing the core book should be increasingly able to:

1. Explain what happens from a tap, voice command, sensor reading, or network request to a human-visible result.
2. Recognize the role of major hardware, software, data, network, security, and manufacturing components.
3. Inspect technology using safe, reproducible methods.
4. Run labs on accessible hardware, commodity hardware, simulations, traces, or supplied datasets.
5. Distinguish observation from inference.
6. Explain what evidence actually supports.
7. Identify where a user-visible failure can originate.
8. Connect technical mechanisms to accessibility, ethics, privacy, equity, safety, economics, and public infrastructure.
9. Move from:
   - "I use technology"
   to:
   - "I can inspect, test, build, explain, and improve technology."
10. Produce portfolio evidence rather than only quiz answers.

# 6. Reader pathways

Every chapter supports the same real system at multiple levels.

## Explorer

Starting point:

- no technical background required.

Evidence expectation:

- label an experience map,
- identify major components,
- explain the path in ordinary language,
- complete a teach-back.

## Operator

Starting point:

- regularly uses devices/software.

Evidence expectation:

- run a guided test,
- interpret status,
- read logs,
- inspect a measurement,
- identify a likely failure domain.

## Builder

Starting point:

- student, maker, or career changer.

Evidence expectation:

- modify code,
- change configuration,
- construct a small system,
- document behavior and tradeoffs.

## Engineer

Starting point:

- undergraduate learner or practitioner.

Evidence expectation:

- measure performance,
- diagnose failure,
- reason about architecture,
- explain constraints,
- compare alternatives.

## Researcher

Starting point:

- graduate learner or investigator.

Evidence expectation:

- formulate a hypothesis,
- define variables,
- design an experiment,
- report uncertainty,
- identify limitations,
- separate correlation from causation.

## Educator

Starting point:

- teacher, mentor, tutor, parent, family guide, or community educator.

Evidence expectation:

- facilitate discussion,
- adapt a lab,
- assess teach-back evidence,
- identify misconceptions,
- differentiate instruction.

# 7. Authenticity rule

Simplicity must come from explanation and sequencing.

It must **not** come from replacing authentic technology with fake or toy concepts.

A beginner may receive:

- a simpler diagram,
- a smaller vocabulary set,
- fewer simultaneous layers,
- a strong analogy,
- guided steps.

But the underlying technology must remain real.

# 9. Device truth-status requirements

Every device-related statement must be classified.

Allowed labels:

- `implemented`
- `validated prototype`
- `simulated`
- `requirement`
- `hypothesis`
- `future concept`

Do not blur these states.

If the publication shows an educational exploded view that is not an exact manufactured device, label it:

> Representative educational architecture

If a specific released hardware revision is shown, record:

- revision,
- source,
- commit/tag,
- date,
- reviewer.

# 15. Stability Contract

The Stability Contract is a signature concept across the publication.

Definition:

> A user experience exists only while multiple hidden technical conditions remain within acceptable bounds.

Possible contract dimensions:

- delay,
- variation/jitter,
- throughput,
- loss,
- compute availability,
- scheduling,
- memory availability,
- storage responsiveness,
- rendering time,
- power,
- temperature,
- radio quality,
- service availability,
- permissions,
- identity/trust,
- adaptation behavior.

A system can remain technically "connected" while the human experience has already failed.

The publication must teach that distinction.

# 16. Evidence integrity

Non-negotiable:

- no fabricated device capabilities,
- no fabricated benchmarks,
- no fabricated deployments,
- no fabricated awards,
- no fabricated partnerships,
- no fabricated learner outcomes,
- no fabricated community outcomes.

Every measured claim must identify, where applicable:

- hardware,
- software version,
- test conditions,
- number of repetitions,
- units,
- raw data,
- uncertainty,
- limitations.

Concept diagrams must be labeled conceptual.

Implementation diagrams must match a specific released or archived system state.

Screenshots/logs must be scrubbed for:

- secrets,
- tokens,
- identifiers,
- private communication,
- private location information.

AI-assisted content must be reviewed for:

- correctness,
- provenance,
- bias,
- reproducibility.

# 20. Editorial defaults

Unless Edmund explicitly changes them:

- Author credit: Edmund Gunn, Jr.
- Named contributors credited by role.
- Reader range: middle-school-accessible explanations with optional engineering/research depth.
- Voice: warm, direct, curious, precise about evidence, never condescending.
- First release: six-chapter Concept Edition.
- Hardware assumptions: Device Quartet narrative spine plus commodity/no-device alternatives.
- Technical depth: real terminology and architecture revealed progressively.
- Assessment: evidence, teach-back, reflection, portfolio artifacts—not recall alone.
- Update cadence: versioned editions with public errata and dated technology updates.

# 21. Repository-derived fact rule

Before a gunnchOS/WAIKE repository fact enters manuscript prose:

1. inspect current accepted `main`,
2. identify exact source file/artifact,
3. record commit SHA,
4. record evidence type,
5. classify truth status,
6. identify limitations,
7. register the claim.

Old README text, planning documents, issues, PR descriptions, stale branches, chat messages, and unmerged work are not sufficient evidence of present capability.

---

# 22. Publication success test

A successful reader should be able to:

- identify a system element,
- explain its role,
- connect it to an experience,
- observe or measure something about it,
- interpret evidence without overclaiming,
- build or modify something,
- explain a failure,
- communicate the concept to another person,
- connect the skill to a professional role,
- understand at least one societal consequence.
